# Authority wire в Apiary: предложение поправки под подписи waggle

Статус: **ЧЕРНОВИК, ждёт ревью**, 2026-09-24. Не нормативный документ. Предложение ничего не меняет в принятом информативном дизайне `apiary-design-2026-09-08`: [`docs/apiary/authority-wire.md`](../../apiary/authority-wire.md) и интерактивное руководство, собранное из принятого снимка, остаются байт-в-байт прежними, пока рецензированное принятие не перепишет эту главу и не пересоберёт руководство с новой принятой ссылкой на источник. Источник заменяющего дизайна: `waggle/spec/waggle.md` (черновик v4; имя, SSHSIG, мультиподпись и провайдеров подписи оператор утвердил 2026-09-24). Связанные черновики: [минимальный роадмап](minimal-roadmap.ru.md), [трек](track.ru.md).

## Зачем

Оркестраторам task-board и Apiary от подписи нужно одно и то же: отправителя нельзя подделать ни на каком транспорте, проверка работает офлайн, одобрять могут несколько сторон. waggle — слой сообщений, выбранный для оркестраторов task-board и их исполнителей; это отдельный публичный Go-модуль, который должны использовать и task-board, и Apiary.

Если Apiary сохранит собственный формат прообраза, одни и те же принципалы будут подписывать два формата, с двумя реестрами ключей и двумя проверяющими. Если записи полномочий Apiary поедут в конвертах waggle, останется одна модель идентичности, один реестр и один конвейер проверки. Появится и то, чего в принятом протоколе нет: соподписи, привязанные к ролям, и уровень доверия к железу ключа.

## Предлагаемое изменение

1. **Контейнер подписи.** Подписанная запись едет как конверт waggle. `payload` — base64url точных байт CCJ неподписанной записи (правила каноникализации и ограниченного JSON из `:60` не меняются, полезная нагрузка никогда не сериализуется заново). `sigs` — список из одной или нескольких записей SSHSIG над теми же байтами. Подписываемая структура SSHSIG (магия `SSHSIG`, namespace, алгоритм хеша, SHA-512 полезной нагрузки) заменяет прообраз `APIARY\0` из `:62`.
2. **Разделение доменов переезжает в namespace.** То, что связывал префикс прообраза (`schema_version`, `record_type`), теперь связывает namespace SSHSIG вместе с ролью подписанта, например `OperationIntent.apiary-proposal-1@apiary` для автора и `approve.OperationIntent.apiary-proposal-1@apiary` для одобряющего. Точное написание открыто (вопрос 1). Подпись, сделанная для одного типа записи, версии схемы или роли, не проходит проверку для другого.
3. **Мультиподпись по ролям.** Каждая запись называет свою роль: `author` (выпускающий подписант узла или оркестратор), `approver` (оператор), `endorser` (родительский оркестратор). Полезная нагрузка называет ожидаемых соподписантов, так что автор связывает себя с тем одобряющим, которого попросил. Закоммиченная политика говорит, каким типам записей нужны какие роли; лишние подписи никогда ничего не дают. Принятое правило, что любой зарегистрированный узел ядра может остановить работу в одиночку (`:13`), остаётся выразимым как политика, требующая для `HaltRequest` только `author`.
4. **Ключи, сертификаты и реестр.** Сертификат ключа из `:94` отображается на сертификаты OpenSSH (подписывающий CA, принципалы, окно действия, серийный номер, key id). Привязка к проекту и роли едет расширениями сертификата, которые проверяет проверяющий. Закреплённый корень проекта становится закоммиченным реестром `allowed_signers`, который читается на закреплённой ревизии, рядом со списком отзыва ключей и файлом политики. Сертификаты OpenSSH одноуровневые, поэтому цепочка до корня проекта выражается так: каждый ключ CA перечисляется в реестре со своими принципалами и namespace, а если вторая сторона должна поручиться в момент сообщения, ставится соподпись.
5. **Провайдеры подписи и уровень доверия.** Подписывание идёт через подключаемых провайдеров: `ssh-agent` для обычных ключей, FIDO и ключей Secure Enclave, которые видны через агента; позже отдельный помощник Secure Enclave, TPM и PIV. Проверяющие при регистрации записывают уровень доверия (`software` < `hardware-bound` < `attested`), а факт `user_verified` для каждой подписи берётся из флагов FIDO, если формат его несёт. Политика задаёт минимальный уровень доверия для каждой роли и типа записи и явный запасной путь для операторов без аппаратных ключей. Ограничения подписанта узла из `:96` не меняются: провайдеры стоят за подписантом узла, и контекст модели никогда не доходит до ключа.
6. **Алгоритмы ключей.** Ed25519 остаётся вариантом по умолчанию для программных ключей. SSHSIG также несёт ключи FIDO (`sk-ssh-ed25519@openssh.com`, `sk-ecdsa-sha2-nistp256@openssh.com`) и ключи ECDSA P-256 из Secure Enclave. Допустимые типы ключей для каждой роли фиксирует политика, они никогда не выбираются по сообщению, что сохраняет запрет на откат из `:62`.
7. **Кадр XMPP.** Элемент `<envelope>` из `:104-110` несёт конверт waggle вместо голого подписанного объекта CCJ (меняется значение атрибута `encoding`, его написание открыто). XML остаётся неподписанным. XMPP остаётся носителем для федерации; локальный носитель waggle, NATS JetStream и board-server перевозят те же байты конверта.
8. **Подтверждения.** Прикладные подтверждения из `:122` отображаются на квитанции waggle (`received_durable`, `delivered`, `read`, `applied`, `rejected:<reason>`, `expired`), которые подписывает принимающий хост; `in_reply_to` и дайджест оригинала сохраняются.

## Что остаётся

- Каноничные байты CCJ и правила ограниченного JSON (`:60`) для полезной нагрузки.
- Область защиты от повторов, ключи дедупликации, `conflicting_duplicate` и запрет понижения (`:98`); waggle дедуплицирует по ключу той же формы с дайджестом полезной нагрузки.
- Закрытый интерфейс подписанта узла (`:96`).
- Ограничения размеров и протокол артефактов (`:92`, `:110`, `:128`) с поправкой на более крупные подписи (см. последствия).
- Семантика полномочий: подпись доказывает, кто сделал утверждение, а не что утверждение истинно; гранты, аренды, fencing, правила остановки и возобновления и уровни кворума L0–L2 не меняются.

## Последствия

- Сохранённые записи можно проверить офлайн штатным OpenSSH (`ssh-keygen -Y verify`) и реестром на записанной ревизии.
- Apiary и task-board пользуются одной реализацией идентичности, реестра и проверки (модуль waggle) вместо двух.
- Запись SSHSIG включает открытый ключ или сертификат подписанта, поэтому весит несколько сотен байт, а не 64 байта голой подписи Ed25519. Ограничения конверта и станзы из `:110` должны учитывать все подписи, которые может потребовать политика.
- Меняются проверочные векторы: векторы подписи и проверки SSHSIG (неверный namespace, неверная роль, изменённый байт, просроченный сертификат, отозванный ключ, отсутствующая соподпись, недостаточный уровень доверия) заменяют векторы прообраза.

## Открытые вопросы

1. Написание namespace для типов записей Apiary, версий схем и ролей; использует ли Apiary семейство namespace `@apiary` или делит классы waggle для пересекающихся видов сообщений (cancel, halt).
2. Какие поля сертификата ключа Apiary (проект, аудитория, роли) становятся расширениями сертификатов OpenSSH, а какие остаются опциями реестра.
3. Как ревизии реестра и списка отзыва питают контрольную точку отзыва и монотонную верхнюю отметку authority.
4. Каким типам записей нужна подпись `approver` или `endorser` (например `ResumeAuthorization` или остановка работы чужого владельца).
5. Значение атрибута `encoding` и согласование версий для элемента XMPP.
6. Определяет ли будущая нормативная грамматика `apiary-spec` конверты SSHSIG сама или ссылается на спецификацию waggle.
